## 1. Η μεγάλη εικόνα

```
          k6 (εικονικοί χρήστες: ανοιχτό μοντέλο, μίξη 7 endpoints)
                         │ HTTP
                         ▼
   ┌───────────────── Kubernetes (kind, 1 κόμβος στο laptop) ─────────────────┐
   │  ingress-nginx ── μετρά κάθε αίτημα: διάρκεια, status (= ό,τι βλέπει ο χρήστης)
   │        │                                                                   │
   │        ▼                                                                   │
   │  backend pods (Node.js, 1 πυρήνας το καθένα, 1–3)   ▲ scale / restart      │
   │     readiness /ready · liveness /health             │ (μόνο μέσω tools)    │
   │        │ /metrics (ανά pod)                         │                      │
   │        ▼                                            │                      │
   │  Prometheus ◀── cAdvisor (CPU ανά container) ◀── kube-state-metrics (pods) │
   └────────│────────────────────────────────────────────│──────────────────────┘
            │ NFR μετρικές κάθε 10 s                      │
            ▼                                            │
   anomaly_detector.py ── ΕΝΑ One-Class SVM ── 3 ανωμαλίες στη σειρά;
            │ ναι                                        │
            ▼                                            │
   agent.py (LLM: smolagents CodeAgent + Gemini) ────────┘
     πριν:  ο κώδικας υπολογίζει γεγονότα, φέρνει μνήμη (ChromaDB) και πρόσφατες ενέργειες
     κατά:  το LLM ερευνά με tools παρατήρησης και εκτελεί ΜΙΑ ενέργεια
     μετά:  ο κώδικας παρακολουθεί το score του SVM: STABLE / UNSTABLE (→ ξαναξύπνημα), σώζει στη μνήμη
```

**Η κεντρική ιδέα:**
- Ένα φθηνό, γρήγορο και ντετερμινιστικό σύστημα (το SVM) αποφασίζει *πότε* κάτι δεν πάει καλά.
- Ένα LLM αποφασίζει *τι* να γίνει.
- Ό,τι πρέπει να γίνεται πάντα με τον ίδιο τρόπο (αριθμητική, φραγμοί, επαλήθευση, μνήμη) το κάνει κώδικας.
- Ό,τι θέλει κρίση το κάνει το LLM.

**Η αλλαγή της φάσης 2:** όλα κρίνονται με βάση τις **μη λειτουργικές απαιτήσεις (NFR)**, δηλαδή ό,τι υπόσχεται η υπηρεσία
στον χρήστη, και όχι με βάση την CPU.

## 2. Kubernetes: τα κομμάτια που χρειάζεσαι

| Έννοια | Τι είναι | Πού το συναντάς |
|---|---|---|
| **Pod** | μία ή περισσότερες διεργασίες που τρέχουν μαζί· εδώ μία διεργασία Node.js | κάθε «αντίγραφο» του backend |
| **Deployment** | δηλώνεις «θέλω N pods με αυτό το template» και ο controller το κρατά αληθινό | `aiops-backend-deployment` |
| **ReplicaSet / revision** | κάθε διαφορετικό template pod γίνεται ένα RS, δηλαδή ένα revision | `get_deployment_history()` |
| **Scale** | αλλάζεις μόνο το N (`spec.replicas`) | `scale_kubernetes_deployment` |
| **Rolling restart** | αλλάζεις ένα annotation στο template, οπότε φτιάχνεται νέο RS: τα νέα pods ανεβαίνουν, και τα παλιά σβήνουν μόλις τα νέα είναι έτοιμα | `restart_kubernetes_deployment` |
| **Readiness probe** | ο kubelet ρωτά συχνά «είσαι έτοιμο;». Αν όχι, το pod **βγαίνει από την κυκλοφορία** (δεν του στέλνεται κίνηση), χωρίς restart | `/ready`: κάθε 5 s, timeout 2 s, 3 αποτυχίες |
| **Liveness probe** | «ζεις;». Αν όχι, ο kubelet **κάνει restart** το container | `/health`: κάθε 10 s, timeout 5 s, 3 αποτυχίες |
| **Ingress** | η «πόρτα» του cluster: δρομολογεί HTTP στα pods ενός Service, και εδώ μετρά κάθε αίτημα | ingress-nginx v1.15.1 |
| **HPA** | ο ενσωματωμένος autoscaler (δες §8) | `4-load-testing/baselines/hpa.yaml` |
| **requests / limits** | πόση CPU «κλείνει» ένα pod και πόση επιτρέπεται να χρησιμοποιήσει | `cpu: "1"` και τα δύο |

**Γιατί η καλή πρακτική θέλει ρηχό liveness:** αν το liveness ελέγχει μια εξάρτηση, για παράδειγμα τη βάση, και η βάση πέσει
για λίγο, **όλα** τα pods κάνουν restart μαζί (restart storm), χωρίς κανένα όφελος. Γι' αυτό:
- το liveness ρωτά μόνο «ζει η διεργασία;»·
- το readiness ρωτά «μπορώ να εξυπηρετήσω τώρα;».

Αυτό εξηγεί γιατί στο stuck το Kubernetes **βγάζει** το pod από την κυκλοφορία αλλά **δεν** το διορθώνει.

**Γιατί 1 πυρήνας ανά pod:**
- Το Node.js τρέχει JavaScript σε ένα νήμα, άρα 1 πυρήνας είναι το φυσικό του όριο.
- Ένα login (bcrypt) θέλει ~71 ms CPU. Χωρά λοιπόν σε ένα παράθυρο CFS των 100 ms, και ο περιορισμός της CPU παγώνει το pod
  (throttling) μόνο όταν πραγματικά συσσωρεύονται αιτήματα.

## 3. Παρατηρησιμότητα: Prometheus και οι μετρικές NFR

### 3.1 Prometheus σε μία παράγραφο
Το Prometheus διαβάζει κάθε λίγα δευτερόλεπτα (scrape) αριθμούς από endpoints `/metrics` και τους κρατά ως χρονοσειρές.
Οι περισσότεροι είναι **counters**, δηλαδή μόνο αυξάνονται («συνολικά αιτήματα»). Μας ενδιαφέρει ο *ρυθμός* τους:
- `rate(x[1m])`: αύξηση ανά δευτερόλεπτο στο τελευταίο λεπτό·
- `histogram_quantile(0.95, …)`: εκτίμηση του p95 από τους «κουβάδες» ενός histogram.

### 3.2 NFR και RED
- **NFR (non-functional requirements):** *πώς* πρέπει να λειτουργεί μια υπηρεσία (γρήγορα, αξιόπιστα, με λογικό κόστος), όχι
  *τι* κάνει. Εδώ:
  - **p95 < 0.35 s**·
  - **σφάλματα < 1%**·
  - **το πολύ 3 pods**.
- **RED:** το κλασικό σύνολο μετρικών για υπηρεσίες: **R**ate (αιτήματα/s), **E**rrors (σφάλματα), **D**uration (διάρκεια).
  Είναι τα συμπτώματα που νιώθει ο χρήστης.
- **«Συναγερμός στα συμπτώματα, όχι στις αιτίες»** (Google SRE): η CPU είναι αιτία, και μια ψηλή CPU μπορεί να είναι
  απολύτως εντάξει. Το αργό latency είναι σύμπτωμα και πάντα μετράει.

### 3.3 Οι μετρικές (`3-ai-agent/nfr_metrics.py`, ένα αρχείο για όλους)

| Μετρική | PromQL (απλοποιημένα) | Πηγή |
|---|---|---|
| `throughput` | `sum(rate(nginx_ingress_controller_requests{host="mwtback.aiops"}[1m]))` | ingress (κάθε status) |
| `error_rate` | ίδιο, με `status=~"5.."`, διά throughput | ingress |
| `latency_p95` | `histogram_quantile(0.95, sum by (le) (rate(nginx_ingress_controller_request_duration_seconds_bucket[1m])))` | ingress |
| `replicas` | `kube_deployment_spec_replicas` (πόσα ζητήσαμε) | kube-state-metrics |
| `ready_replicas` | `kube_deployment_status_replicas_available` (έτοιμα pods) | kube-state-metrics |
| `rps_per_pod` | throughput / replicas | υπολογισμένο |
| `avg_cpu_per_pod` | `sum(rate(container_cpu_usage_seconds_total[1m]))` / έτοιμα pods | cAdvisor: **μόνο** για διάγνωση και για το HPA |

**Γιατί στο ingress:** εκεί είναι ό,τι βλέπει ο χρήστης.
- Το histogram της εφαρμογής ξεκινά να μετρά όταν τρέξει η JavaScript του αιτήματος. Αν το event loop είναι μπλοκαρισμένο
  (cpuhog), η αναμονή πριν δεν μετριέται. Ήταν το τυφλό σημείο της φάσης 1.
- Το ingress μετρά από τη στιγμή που φτάνει το αίτημα ως την απάντηση.
- Το ingress στήθηκε με buckets ίδια με του backend (0.025 … 0.35 … 10 s), ώστε το 0.35 να είναι όριο κουβά και η εκτίμηση
  να είναι ακριβής εκεί που μετράει.

### 3.4 p95 και histograms
- Το p95 είναι **χρόνος**: αν ταξινομήσεις τα αιτήματα κατά διάρκεια, είναι η διάρκεια στη θέση 95%.
- Το histogram δεν κρατά κάθε διάρκεια. Μετρά πόσα αιτήματα έπεσαν σε κάθε κουβά, και το `histogram_quantile` κάνει
  γραμμική παρεμβολή μέσα στον κουβά.
- Γι' αυτό το p95 «πηδά» ανάμεσα σε σκαλοπάτια όταν οι αλλαγές είναι μικρές. Και γι' αυτό το μοντέλο αντιμετωπίζει ως ίδια
  κάθε p95 κάτω από 0.2 s (§4.4).

### 3.5 Τα σήματα διάγνωσης ανά pod (στο `get_pod_breakdown`)
- **Event-loop lag:** πόσο αργεί το Node να εξυπηρετήσει ένα timer που έπρεπε να τρέξει τώρα. Υγιές ~0.01 s. Όταν κάτι
  μπλοκάρει το νήμα (cpuhog), ~1.1–1.2 s.
- **CPU ανά αίτημα** = CPU του pod / αιτήματα του pod. Υγιές ~0.0084 core-s, με μέγιστο 0.016.
  - Αν αυξηθεί η κίνηση, ανεβαίνει η CPU, αλλά **όχι** η CPU ανά αίτημα.
  - Αν η CPU ανά αίτημα γίνει πολλαπλάσια, κάτι άλλο καίει CPU. Στο cpuhog ήταν ~0.019 με 1.0 πυρήνα.
- **Έτοιμο ή όχι, 5xx, logs:** στο stuck το pod είναι μη έτοιμο και τα logs λένε «DB connection pool exhausted».

## 4. Ανίχνευση ανωμαλιών

### 4.1 Γιατί «one-class»
Δεν έχουμε δεδομένα για όλα τα πιθανά σφάλματα, αλλά έχουμε άφθονα **υγιή**. Ένα one-class μοντέλο μαθαίνει μόνο το σχήμα
του υγιούς και επισημαίνει ό,τι πέφτει έξω, όποια κι αν είναι η αιτία (novelty detection).

### 4.2 One-Class SVM σε απλά λόγια
- Κάθε μέτρηση γίνεται ένα σημείο σε χώρο 4 διαστάσεων (§4.4).
- Το μοντέλο κρατά λίγα «αντιπροσωπευτικά» υγιή σημεία (support vectors) και για κάθε νέο σημείο υπολογίζει πόσο κοντά τους
  είναι: `score(x) = Σ αᵢ · exp(−γ‖x − xᵢ‖²) − ρ`.
  - `exp(−γ·απόσταση²)` είναι ο **RBF kernel**: 1 πάνω σε υγιές σημείο, και πλησιάζει το 0 όσο απομακρύνεσαι.
  - **≥ 0** = υγιές, **< 0** = ανωμαλία.
- **γ:** πόσο «τοπικό» είναι το σύνορο. Εδώ 0.5 (v11· v10: 0.2), επιλεγμένο με τον κανόνα της §4.5. Είναι η μόνη επιλογή
  του μοντέλου.
- **ν:** ανώτατο ποσοστό υγιών σημείων που επιτρέπεται να μείνουν έξω. Εδώ 0.02. Έμειναν 8 support vectors (v10: 6).
- **Κορεσμός, και πώς τον λύνει το v10.** Μακριά από όλα τα υγιή σημεία οι όροι exp γίνονται ~0, άρα η decision function
  «φρενάρει» στο −ρ. Στο v9 το score ήταν η ίδια η decision function: −0.537 σε κάθε σοβαρό σφάλμα, και η πορεία δεν
  φαινόταν.
- **Το score, από το v10** (`health_model.score`), είναι η ίδια απόφαση, διαβασμένη ως απόσταση:
  - αν d ≥ 0: min(1, d / d_ref), όπου d_ref = ο διάμεσος d των υγιών μετρήσεων αυτού του αριθμού pods. Άρα **0..1, με 1 =
    τυπικά υγιές**·
  - αν d < 0: **−√(ln(ρ / Σ αᵢ·exp(−γ‖x − xᵢ‖²)) / γ)**. Είναι μια απόσταση από την υγιή περιοχή, στις μονάδες των
    εισόδων. Με ένα μόνο support vector σε απόσταση r θα ήταν √(r² − r₀²), όπου r₀ η ακτίνα του συνόρου: 0 πάνω στο σύνορο,
    και ≈ r μακριά. Ο λογάριθμος δεν «φρενάρει».
  - Το πρόσημο είναι πάντα αυτό του SVM (ίδιο σύνορο).
  - Παραδείγματα (1 pod, 57 rps): p95 0.35 s → −0.48· 1% σφάλματα → −0.88· stuck (p95 4.6 s, 50% σφάλματα) → −50· 100%
    σφάλματα → −100. Σπατάλη (3 pods, 105 rps) → −0.38.

### 4.3 Γιατί όχι Isolation Forest (θα σε ρωτήσουν)
- Το Isolation Forest κόβει τυχαία **μέσα στο εύρος** των δεδομένων εκπαίδευσης. Ένα σημείο πέρα από το άκρο ακολουθεί πάντα
  το ίδιο μονοπάτι με το άκρο, άρα παίρνει **ίδιο score όσο μακριά κι αν είναι**.
- Έτσι έχανε τη μονοκατευθυντική απόκλιση: τη σπατάλη, όπου πέφτει μόνο το φορτίο, και το «κόλλημα», όπου ανεβαίνει μόνο
  το latency.
- Το One-Class SVM βασίζεται σε απόσταση.
- Αποδείχτηκε στη φάση 1 (`design_decisions.md` Α2–Α3, `figures/detector_evidence.py`).

### 4.4 Οι είσοδοι και ο μετασχηματισμός (`health_model.transform`)

Οι είσοδοι είναι **σε μονάδες NFR, χωρίς ρυθμιζόμενα βάρη** (v11, Α30). Για latency και σφάλματα ισχύει ο ίδιος ορισμός:
**0 = το ασφαλές επίπεδο, 1 = η NFR.**

| Είσοδος | Μετασχηματισμός | Γιατί |
|---|---|---|
| φορτίο | ln(συνολικό throughput) | οι ζώνες είναι αναλογικές (2 pods: 66.5→165): σε λογαρίθμους, το «20% κάτω» είναι ίδια απόσταση παντού. Η μονάδα δεν εξαρτάται από το πλάτος των ραμπών |
| p95 | ln(max(p95, **0.25**) / 0.25) / ln(**0.35** / 0.25) | 0 στα 0.25 s, 1 στα 0.35 s. Κάτω από το ασφαλές όλα μετρούν ίδια: **το πιο γρήγορο δεν είναι ποτέ χειρότερο** (μονοτονία εξ ορισμού). Σε λογαρίθμους, γιατί ο θόρυβος του p95 είναι αναλογικός |
| σφάλματα | (max(σφάλματα, **0.1%**) − 0.1%) / (**1%** − 0.1%) | 0 στο 0.1%, 1 στο 1%. Μέσα στο ασφαλές όλα μετρούν ίδια, όπως στο latency |
| pods | 100 × replicas (`POD_SEPARATION`) | κάθε αριθμός pods έχει τη δική του υγιή περιοχή: exp(−γ·100²) = 0 |

**Στο v10** οι είσοδοι είχαν βάρη από grid: φορτίο τυποποιημένο × 1, latency 2 × ln(max(p95, 0.25) / 0.35), σφάλματα / 1%,
pods × 8. Το offline διαγνωστικό (27/10) έδειξε τι έκαναν:
- το βάρος των pods τίποτα (8, 12 ή 100: ίδια απόφαση)·
- η τυποποίηση σχεδόν τίποτα (τυπική απόκλιση 0.97)·
- το βάρος του latency όριζε μόνο μια μονάδα, που μετά την αντιστάθμιζε το γ.

Στο v11 τις μονάδες τις ορίζουν οι NFR, και η μόνη επιλογή είναι το γ.

**Χωρίς CPU και throttling:** οδηγός είναι οι NFR. Το φορτίο δίνει την έγκαιρη προειδοποίηση σε μονάδες που καταλαβαίνει ο
χρήστης.

**Γιατί το πάτωμα του latency είναι το 0.25 s και όχι πιο χαμηλά (Α28.1).** Η πρώτη δηλωμένη μέθοδος ήθελε το SVM να μάθει
«τι latency είναι φυσιολογικό για αυτό το φορτίο», δηλαδή να βλέπει και διαφορές κάτω από το 0.25 s. Απέτυχε: στα υγιή
δεδομένα το latency ανεβαίνει μαζί με το φορτίο, και το σύνορο του RBF αντιστρέφεται στα άκρα των ζωνών. Για παράδειγμα,
1 pod στα 91.8 rps ήταν ανωμαλία με p95 0.08 s και υγιές με 0.10–0.19 s. Ένα RBF SVM δεν μπορεί να είναι ταυτόχρονα
ευαίσθητο κάτω από το ασφαλές και μονότονο. Κρατήσαμε τη μονοτονία.

**Τι μαθαίνει τελικά το SVM, και πού μπαίνει το latency** (ανάλυση 2026-10-27).
- **Στην εκπαίδευση το latency δεν αλλάζει.** Οι 181 υγιείς μετρήσεις έχουν όλες p95 ≤ 0.25 s, άρα όλες παίρνουν latency
  −0.67 (το πάτωμα). Τα σφάλματα είναι 0 σε όλες. Από τα δεδομένα το SVM μαθαίνει μόνο **ποιο φορτίο είναι υγιές για κάθε
  αριθμό pods**: 1 pod 4–87, 2 pods 73.7–162.4, 3 pods 123.7–251.5 rps.
- **Το latency μπαίνει με δύο τρόπους:**
  1. **Έμμεσα, στις ζώνες.** Οι ζώνες είναι όρια latency, μεταφρασμένα σε φορτίο:
     - η συλλογή ανέβηκε ως το ασφαλές φορτίο του πίνακα χωρητικότητας, όπου p95 ≤ 0.25 s·
     - το φίλτρο έβγαλε τις 7 μετρήσεις με p95 0.26–0.38 s (6 στο 1 pod στα 83–92 rps, 1 στα 3 pods στα 246 rps).

     Άρα «1 pod υγιές ως 87 rps» σημαίνει «ως εκεί το p95 έμεινε κάτω από 0.25 s».
  2. **Άμεσα, στην εκτέλεση, ως απόσταση πάνω από τα 0.25 s.** Το SVM ενώνει αυτή την απόσταση με την απόσταση του
     φορτίου από τη ζώνη, σε μία:

     | 1 pod | Ανωμαλία από p95 (**v12**, γ 0.1) | (v11, γ 0.5) | (v10) |
     |---|---|---|---|
     | 30 rps (μέση της ζώνης) | 0.325 s | 0.27 s | 0.33 s |
     | 57 rps | 0.306 s | 0.28 s | 0.32 s |
     | 80 rps | 0.277 s | 0.27 s | 0.285 s |
     | 87 rps (άκρη της ζώνης) | 0.257 s | 0.255 s | 0.26 s |

     Στα 2 και 3 pods (v12): 0.285 / 0.28 s στη μέση και 0.26 s στην άκρη, όπως στο v11 (v10: 0.305 / 0.30 και 0.265 / 0.26).
     Το πόσο ανέχεται το ορίζει το γ, όπως το διάλεξαν τα probes (0.25 s υγιές, 0.35 s ανωμαλία σε κάθε φορτίο, καμία
     τρύπα), **όχι** η διακύμανση του latency στα δεδομένα. Το γ 0.1 του v12 είναι πιο ομαλό από το 0.5 του v11: δεν έχει
     τρύπες, και γι' αυτό ανέχεται περισσότερο στη μέση της ζώνης του 1 pod.
- **Το score ως προς το p95** (1 pod, 57 rps):

  | p95 | ≤ 0.25 s | 0.28 | 0.30 | 0.35 (NFR) | 0.50 | 0.70 | 1.0 | 2.0 |
  |---|---|---|---|---|---|---|---|---|
  | score v12 | 0.59 | 0.40 | 0.11 | −0.80 | −2.0 | −3.0 | −4.1 | −6.2 |
  | score v11 | 1.00 | −0.05 | −0.43 | −0.94 | −2.0 | −3.0 | −4.1 | −6.2 |
  | score v10 | 0.76 | 0.58 | 0.30 | −0.48 | −1.3 | −2.0 | −2.7 | −4.1 |

- **Τι ξύπνησε τον agent στην καμπάνια του v10** (στις ίδιες χρονοσειρές, το v11 ξυπνά στα ίδια δευτερόλεπτα):
  - **Κανονικό φορτίο** (4 runs, 1→2 pods): η σειρά ανωμαλιών ξεκίνησε μόλις το φορτίο πέρασε τα ~87–88 rps. Σε 3 από τα 4
    runs την ξεκίνησε **το φορτίο μόνο**. Σε δύο από αυτά το p95 ήταν ακόμα 0.20 και 0.24 s.
    - Το latency έκανε μετά το score πιο αρνητικό (v10): −0.83 με p95 0.37 s, όταν το φορτίο μόνο θα έδινε −0.26.
    - Σε ένα run (03:40) ξεκίνησε τη σειρά 10 s νωρίτερα (p95 0.264 s στα 87.3 rps, όπου το φορτίο μόνο έδινε 0.00).
  - **Cpuhog:** το φορτίο ήταν κανονικό (56 rps). Στην αφύπνιση το έδειξε το latency (1.5–1.8 s), και σε 3 από τα 4 runs
    μόνο αυτό, με 0% σφάλματα (στο τέταρτο 7%).
  - **Stuck:** στην αφύπνιση φαίνονταν και τα δύο: p95 4.6 s (τα αιτήματα περιμένουν το pool) και σφάλματα 48–62%. Μόλις το
    readiness βγάλει το pod, το nginx απαντά 503 σε 0.02 s, και από εκεί και πέρα το δείχνουν μόνο τα σφάλματα.
- **Η σωστή διατύπωση.** Δεν λέμε «το SVM μαθαίνει τι latency είναι φυσιολογικό για κάθε φορτίο». Λέμε: «το SVM μαθαίνει το
  υγιές φορτίο ανά αριθμό pods, όπως το όρισε το latency. Latency και σφάλματα μετρούν ως απόσταση πάνω από το ασφαλές
  επίπεδο, σε μονάδες NFR.»

### 4.5 Ένα μοντέλο για όλους τους αριθμούς pods
- **Τι ζήτησαν οι καθηγητές:** τον αριθμό pods ως είσοδο, αντί για 3 χωριστά μοντέλα.
- **Ο κίνδυνος:** στη φάση 1, το ενιαίο Isolation Forest μπέρδευε τους αριθμούς pods. «2 pods με λίγο φορτίο» έμοιαζε με
  «υγιές 1 pod».
- **Πώς λύθηκε:** με βάρος στα pods (8×), ώστε οι ζώνες να μένουν χωριστές.
- **Πώς ελέγχθηκε:** με probes «σπατάλη» και «μετά από scale-down» για κάθε αριθμό pods.

**Γιατί μία σάρωση του φορτίου ελέγχει κάθε μέτρηση (Α31).**
- Όλες οι υγιείς μετρήσεις έχουν latency και σφάλματα στο ασφαλές επίπεδο, άρα x_lat = x_err = 0. Επομένως **όλα τα support
  vectors είναι πάνω στον άξονα του φορτίου.**
- Για N pods το άθροισμα των kernels γίνεται γινόμενο:

  Σ αᵢ·exp(−γ‖x − sᵢ‖²) = exp(−γ·r²) · K_N(ln rps),  με r² = x_lat² + x_err²

  Τα support vectors των άλλων αριθμών pods δίνουν exp(−γ·100²) = 0.
- Άρα **υγιές ⟺ r² ≤ ln(K_N/ρ)/γ**. Από μία συνάρτηση του φορτίου (K_N) βγαίνουν:
  - η υγιής ζώνη (όπου K_N ≥ ρ)·
  - πόσο latency και πόσα σφάλματα ανέχεται σε κάθε φορτίο (ακτίνα R = √(ln(K_N/ρ)/γ): p95 ως 0.25·1.4^R, σφάλματα ως
    0.1% + 0.9%·R)·
  - η μονοτονία (το exp(−γ·r²) φθίνει πάντα)·
  - «οι NFR είναι ανωμαλία σε κάθε φορτίο» ⟺ max R < 1.
- Μια πυκνή σάρωση του φορτίου (0.5–1000 rps, βήμα 0.25%) βλέπει λοιπόν **κάθε** τρύπα και κάθε συνδυασμό φορτίου, latency και
  σφαλμάτων, όχι μόνο δειγματικά σημεία.

**Πώς επιλέχθηκε (`train_health_baseline.py`, v12):**
- Μόνο το γ: {0.1, 0.2, 0.5, 1}, το ίδιο grid με την Α28, ν 0.02. (Στο v10 και 4 βάρη: 144 συνδυασμοί.)
- Κάθε τιμή κρίθηκε με:
  1. **34 probes-εύρη** (Α31), για κάθε αριθμό pods. Το αποτέλεσμα ενός probe είναι το χειρότερο σημείο του εύρους του:
     - υγιές σε όλη τη ζώνη [1.05·βάση, 0.95·κορυφή] → υγιές·
     - **ένα συνεχές υγιές διάστημα** στη σάρωση → καμία τρύπα, κανένα νησί·
     - κάθε φορτίο ≥ 1.1·κορυφή → ανωμαλία· κάθε φορτίο ≤ 0.8·βάση → ανωμαλία (σπατάλη, για 2 και 3 pods)·
     - **p95 0.35 s σε κάθε φορτίο** → ανωμαλία· **1% σφάλματα σε κάθε φορτίο** → ανωμαλία·
     - N+1 pods μετά από scale-up και N−1 μετά από scale-down → υγιές·
     - 1 pod στα 1.05–4 rps (αδράνεια) → υγιές·
     - stuck, outage, stuck όπως μετρήθηκε (4.6 s, 48%), cpuhog (0.7 s) → ανωμαλία·

  3. **held-out**: εκπαίδευση στις μετρήσεις «προς τα πάνω» και έλεγχος στις «προς τα κάτω», και αντίστροφα·
  4. **κανόνας επιλογής, δηλωμένος πριν το αποτέλεσμα (Α28, ίδιος στις Α30 και Α31):** όλα τα probes → μονότονο → λιγότερες
     held-out αφυπνίσεις → μεγαλύτερο περιθώριο προς θόρυβο → λιγότερες held-out επισημάνσεις → μικρότερο γ.
- **Δεδομένα:** 210 υγιείς μετρήσεις. 181 είναι από τις ράμπες της 23/10 και 29 από τη σκάλα 4 → 1 → 4 rps του 1 pod

  ανωμαλία κινείται σε μονάδες (stuck: −100 → −10 σε 50 s). Άρα **μία μέτρηση αρκεί**, και η επαλήθευση κρίνει μέτρηση

### 4.7 Από πού έρχονται τα δεδομένα (`5-ml-training/`)

## 6. Ο LLM agent

### 6.1 Τι είναι ένας «agent»
Ένα LLM μόνο του παράγει κείμενο. Ένας **agent** είναι ένα LLM σε βρόχο: *σκέψου → κάλεσε ένα εργαλείο → δες το αποτέλεσμα
→ σκέψου ξανά*, ώσπου να δώσει τελική απάντηση. Το μοτίβο λέγεται **ReAct** (Reasoning + Acting). Τα εργαλεία είναι απλές
συναρτήσεις Python.

### 6.2 CodeAgent (smolagents)
- Ο **CodeAgent** γράφει τις ενέργειές του ως **κώδικα Python**, π.χ. `print(get_pod_breakdown())`. Ο κώδικας εκτελείται και
  το output επιστρέφει στο LLM ως παρατήρηση.
- Ο κώδικας τρέχει στον `LocalPythonExecutor`, έναν interpreter με **λευκή λίστα imports** (όχι `os`, `subprocess`,
  `kubernetes`). Ο μόνος δρόμος προς το cluster είναι τα εργαλεία μας, που έχουν φραγμούς.
- **LiteLLM:** κοινή διεπαφή για όλους τους παρόχους. Αλλαγή μοντέλου = αλλαγή ενός string.
- **`RetryingLiteLLMModel` (`agent.py`):** σε 429/503/timeout ή κενή απάντηση ξαναδοκιμάζει μετά από 5, 15 και 30 s, και
  μετά πάει στο εφεδρικό μοντέλο (`gemini-2.5-flash`).

### 6.3 Η ροή ενός περιστατικού (`trigger_ai_agent` στο `agent.py`)
```
ΠΡΙΝ (κώδικας)  γεγονότα (_computed_facts) · μνήμη: 2 όμοια επιτυχημένα (ChromaDB) · πρόσφατες ενέργειες 15' → prompt
ΚΑΤΑ (LLM)      ταξινόμηση → (παρατηρήσεις) → μία ενέργεια → final_answer("Root cause: ... Action: ...")
ΜΕΤΑ (κώδικας)  ενέργειες από τα ίδια τα tools (όχι από το κείμενο) → επαλήθευση με το score
                → σώσιμο στη μνήμη (resolved/failed) → εγγραφή στο incident_log.csv
                → UNSTABLE: αν ήταν scale-down, επαναφορά pods· αλλιώς «ξαναξύπνα με»
```

### 6.4 Τα υπολογισμένα γεγονότα (`_computed_facts`)
Τα LLM κάνουν λάθη στην αριθμητική, γι' αυτό τα γεγονότα τα υπολογίζει ο κώδικας:
- **Score και εξήγηση** (`health_model.explain`, από την εξήγηση του detector), π.χ. στο stuck: «Health score −62.32 (0 to 1
  = healthy, 1 = typical; below 0 = anomalous …)», «p95 latency 4.60 s is above the healthy maximum … (objective 0.35 s);
  62.0% of requests fail (5xx) … (objective 1%)». Στο 2→3 του κανονικού φορτίου: «load per pod 85.5 rps is above the healthy
  maximum 81.1 for 2 pod(s) (under-provisioned); p95 latency 0.23 s is above the healthy maximum 0.19 s (objective 0.35 s)».
  - Τα «healthy maximum» είναι τα εύρη που είδε το μοντέλο στην εκπαίδευση, όχι το σύνορό του· η απόφαση είναι μόνο του SVM.
- **Pods:** «Only 0 of 1 pod(s) are ready».
- **Φορτίο και τάση:** «Load: 171.0 rps on 2 pod(s) (85.5 per pod); trend over the last minute: RISING +21.4 rps per minute».
- **Ελάχιστα pods** (v10): «Minimum pod count the health model calls healthy for this load, and for the 203 rps the trend
  reaches in 90 s (the time until new pods serve): 3. Current: 2».
  - Τι κάνει ο κώδικας (`health_model.min_healthy_pods`): ρωτά το SVM για 1, 2, 3 pods με το φορτίο max(rps, rps + max(0,
    κλίση) × 1.5), latency στο ασφαλές και 0 σφάλματα, και κρατά τον μικρότερο αριθμό που βγαίνει υγιής.
  - Στο v9 ήταν κανόνας: ο μικρότερος N με ασφαλές(N) ≥ max(rps + κλίση × 1.5, rps / 0.85), δηλαδή 15% περιθώριο πάνω στον
    πίνακα χωρητικότητας. Στο v10 το περιθώριο είναι ήδη στα δεδομένα, που σταματούν στο ασφαλές επίπεδο.
- **Η ζώνη του μοντέλου:** «The health model's healthy load band for 2 pod(s) is 73.7–162.4 rps: the load is ABOVE it
  (under-provisioned)». Αλλιώς BELOW (over-provisioned) ή inside. Το «inside» προσθέτει ότι το φορτίο μόνο του δεν εξηγεί
  κακό latency ή σφάλματα.

Η κλίση μπήκε στο v9 μετά από ένα δοκιμαστικό run. Εκεί, στο 96% της χωρητικότητας και με ανοδικό φορτίο, το γεγονός έλεγε
απλώς «within», και ο agent το θεώρησε παροδικό.

### 6.5 Το prompt v9 (ίδιο στο v10) σε μία σελίδα
1. **Στόχοι:** p95 < 0.35 s, σφάλματα < 1%, το πολύ 3 pods και όχι περισσότερα από όσα χρειάζεται το φορτίο.
2. **Βήμα 1, ταξινόμηση:**
   - (A) **χωρητικότητα**, αν ελάχιστα ≠ τωρινά και τα pods είναι έτοιμα·
   - (B) **κάτι άλλο**, ή αν δεν είναι σίγουρος.
3. **2A:** scale στο ελάχιστο. Πάνω αν λείπουν pods, **υποχρεωτικά κάτω** αν περισσεύουν.
4. **2B:** και τα 3 εργαλεία παρατήρησης, ένα ανά βήμα. Μετά:
   - **στοιχεία** κακής κατάστασης στη διεργασία (ERROR / κολλημένη εργασία στα logs, pods μη έτοιμα, lag ή CPU ανά αίτημα
     πολλαπλάσια) → **restart**· οι προειδοποιήσεις που απλώς επαναλαμβάνουν το σύμπτωμα δεν μετράνε·
   - χωρητικότητα τελικά → scale·
   - φταίει πρόσφατη αλλαγή → «No action taken: … needs a human decision», γιατί δεν υπάρχει undo και ένα restart θα την
     ξαναδημιουργούσε·
   - χωρίς στοιχεία και μικρή παραβίαση → «No action» (ο detector θα ξαναξυπνήσει).
5. **Κανόνες:**
   - ένα εργαλείο ανά βήμα·
   - «περισσότερα pods βοηθούν μόνο αν το φορτίο ξεπερνά τα pods· restart μόνο αν η κακή κατάσταση ζει στις διεργασίες»·
   - μην επαναλαμβάνεις ενέργεια που μόλις απέτυχε.
6. **Βήμα 3:** μία ενέργεια. Το σύστημα παρακολουθεί το score και ξαναξυπνά τον agent αν χειροτερέψει.
7. **Βήμα 4:** αναφορά σε επόμενο βήμα από την ενέργεια. **Μην επαληθεύεις μόνος σου**: το κάνει το σύστημα.

| `scale_kubernetes_deployment(replicas)` | ενέργεια | 1–3, ±2 ανά κλήση, cooldown 30 s |
| `restart_kubernetes_deployment()` | ενέργεια (rolling) | cooldown 60 s, μόνο μετά από πλήρη διάγνωση |

Το namespace και το deployment είναι καρφωμένα στον κώδικα. Τα docstrings των εργαλείων είναι μέρος του prompt, γιατί το
smolagents τα βάζει αυτούσια στο system prompt.

### 6.7 Οι τρεις φραγμοί (κώδικας, όχι παράκληση στο prompt)
1. **Πρώτα στοιχεία, μετά ενέργεια.** Αν σε ένα βήμα κληθεί εργαλείο παρατήρησης, οι ενέργειες και το final_answer του ίδιου
   βήματος αρνούνται. Αιτία (φάση 1, v6): το LLM έγραψε «παρατήρηση + scale + απάντηση» σε ένα block, πριν δει τίποτα.
2. **Καμία δηλωμένη ενέργεια χωρίς tool.** Μια τελική απάντηση που δεν ξεκινά με «No action taken» απορρίπτεται, αν δεν
   εκτελέστηκε ενέργεια. Αιτία (v6): το LLM έγραψε «Action: Scale up to 3» χωρίς να καλέσει το εργαλείο.
3. **Διάγνωση πριν από restart.** Το restart αρνείται μέχρι να χρησιμοποιηθούν και τα 3 εργαλεία παρατήρησης. Το scale δεν
   επηρεάζεται. Αιτία (v7): restart κοιτώντας μόνο την εικόνα ανά pod, ενώ η αιτία ήταν στο ιστορικό.

Στην καμπάνια της φάσης 2 κανένας φραγμός δεν χρειάστηκε να αρνηθεί κάτι. Στα δοκιμαστικά runs ο τρίτος αρνήθηκε μία φορά
ένα πρόωρο restart.

### 6.8 Επαλήθευση με την πορεία του score
1. Περιμένει το rollout, το πολύ 90 s.
2. Κάθε 10 s παίρνει μία μέτρηση (τα queries του detector) και το score της.
3. Κρίνει **μέτρηση προς μέτρηση** (`health_model.judge_trajectory`, ο κανόνας σου, v10):
   - **STABLE:** η τελευταία μέτρηση είναι υγιής (score ≥ 0).
   - **Στα πρώτα 10 s μετά το rollout:** μόνο STABLE ή «περίμενε». Η πρώτη μέτρηση μετά από μια ενέργεια μπορεί να βουτήξει
     (ένα νέο pod στα πρώτα του αιτήματα). Στο replay των 61 ενεργειών, η κρίση από τα 0 s έδωσε 6 ψευδή «worse», ενώ η
     κρίση από τα 10 s έδωσε 61/61 STABLE (v12, Α31· ως τον v11 η αναμονή ήταν 60 s, ώσπου το παράθυρο του λεπτού να έχει
     μόνο νέα δεδομένα).
   - **Μέσα στο πρώτο λεπτό** το παράθυρο ανακατεύει το πριν με το μετά. Μια **πτώση** είναι πραγματική: πιο γρήγορα αιτήματα
     δεν μπορούν να ανεβάσουν το p95 ενός παραθύρου. Το «δεν ανεβαίνει» όμως δεν είναι: το p95 μένει στο παλιό επίπεδο ώσπου
     τα αργά αιτήματα από πριν να γίνουν λιγότερα από 5% του παραθύρου, δηλαδή σχεδόν όλο το λεπτό. Γι' αυτό (Α31.1):
     - «worse» από τα 10 s·
     - «not improving» μόνο από τα 60 s. Στο δοκιμαστικό της 1/11 ένα σωστό 1→2 βγήκε ψευδώς UNSTABLE στα +40 s με τον κανόνα
       των 10 s: το p95 έμεινε 0.48 s για 40 s και μετά έπεσε στα 0.24 s.
   - **Μετά:**
     - πέφτει περισσότερο από ε = 0.142 (ο θόρυβος) σε σχέση με την προηγούμενη → **UNSTABLE: worse**·
     - δεν ανεβαίνει πάνω από ε σε 3 μετρήσεις (30 s) → **UNSTABLE: not improving**·
     - αλλιώς, δηλαδή πλησιάζει το υγιές, «περίμενε».
   - Όριο: 4 λεπτά.
4. UNSTABLE → ο detector ξαναξυπνά τον agent αμέσως, έως 2 φορές. Ένα αποτυχημένο **scale-down** το επαναφέρει ο κώδικας.

Παράδειγμα (stuck, 2026-10-27 01:17, μετά το restart): −100.1 → −90.0 → −70.2 → −50.1 → −30.0 → −10.1 → **+0.76 → STABLE**.
Το score ακολουθεί τα σφάλματα του παραθύρου, όσο φεύγουν τα παλιά δεδομένα. Στο v9 η ίδια πορεία ήταν −0.537 για 50 s και
μετά +0.025: χωρίς τον κανόνα «περίμενε ως να γεμίσει το παράθυρο», η επαλήθευση θα έλεγε λάθος «not improving».

### 6.9 Μνήμη (RAG) και πρόσφατες ενέργειες
- **RAG** (Retrieval-Augmented Generation): ανακτάς σχετική πληροφορία (εδώ, παλιά περιστατικά) και τη βάζεις στο prompt.
- **Μακροπρόθεσμη (ChromaDB, `incidents_nfr`):**
  - **Embedding** = το διάνυσμα του μοντέλου (`health_model.embedding`): «όμοιο» σημαίνει «κοντά στον χώρο του SVM». Στη
    φάση 1 τα text embeddings έβαζαν υπερφόρτωση και σπατάλη σχεδόν στην ίδια απόσταση.
  - **Αποθηκεύονται όλα**, με status resolved / failed.
  - **Ανακτώνται** μόνο τα 2 πιο κοντινά resolved, σε απόσταση ≤ 0.43 (`memory_similar_max` του μοντέλου: πόσο απέχει μια
    υγιής κατάσταση από μια πρώιμη υπερφόρτωση). Αλλιώς «NO similar past incident», με το πιο κοντινό μόνο για αναφορά.
  - Στην καμπάνια του v10: 11 από τις 12 αφυπνίσεις κανονικού φορτίου μετά το πρώτο run βρήκαν όμοιο περιστατικό· το πρώτο
    run ξεκίνησε με άδεια μνήμη.
- **Βραχυπρόθεσμη (15 λεπτά):** στη μνήμη του προγράμματος, για να μην επαναληφθεί μια ενέργεια που μόλις απέτυχε.
- **Ο δίσκος του ChromaDB είναι πλέον στο σωστό path (`/data`).** Στη φάση 1 η μνήμη χανόταν σε κάθε restart.

## 8. Η σύγκριση: Kubernetes HPA
- **Πώς δουλεύει:** κάθε ~15 s υπολογίζει `επιθυμητά pods = ⌈pods × τρέχουσα CPU% / στόχος%⌉`, με ανοχή 10%. Πριν κατεβάσει,
  περιμένει τη stabilization window (εδώ 120 s). Βλέπει **μόνο CPU**.
- **Ο στόχος 60%:**
  - Βγήκε από τη μέτρηση χωρητικότητας: 0.0083 core-s ανά αίτημα.
  - Με την ανοχή κλιμακώνει στα ~0.66 πυρήνα ≈ 80 rps ανά pod, δηλαδή κάτω από το ασφαλές κάθε αριθμού pods.
  - Το HPA έχει λοιπόν την **ίδια γνώση** με τον agent.
  - Με το 70% της φάσης 1, τα 2 pods θα έτρεχαν ως ~93 rps το καθένα, πέρα από το ασφαλές τους (82.5).
- **Probes:** ίδια readiness και liveness και στις δύο μεθόδους. Η σύγκριση είναι «Kubernetes μόνο του» έναντι «Kubernetes +
  agent».

## 9. Μεθοδολογία αξιολόγησης

### 9.1 Το harness (`4-load-testing/run_experiment.sh <llm|hpa>`)
1. Καθαρή αρχή: rolling restart, 1 pod, καθαρό ιστορικό revisions, pool tokens, 2 λεπτά αδράνεια.
2. **Μία** στρατηγική τη φορά, γιατί δύο controllers στο ίδιο deployment θα «μάχονταν».
3. Φορτίο k6, με το σφάλμα στο λεπτό 4 αν το σενάριο έχει.
4. Τέλος της στρατηγικής, βαθμολόγηση από το Prometheus (`evaluate_run.py`).

Κάθε run κρατά τον φάκελό του (`eval_…/`):
- `controller.log`: τι είδε και τι σκέφτηκε ο agent·
- `series.json`: οι χρονοσειρές, γιατί το Prometheus κρατά μόνο 10 μέρες·
- η σύνοψη του k6·
- `power.log`: ρεύμα ή μπαταρία ανά 30 s.

### 9.2 Οι μετρικές
| Μετρική | Ορισμός | Τι δείχνει |
|---|---|---|
| `nfr_violation_s` | δευτερόλεπτα με p95 > 0.35 s **ή** σφάλματα > 1% | τι ένιωσαν οι χρήστες |
| `errors_pct` | αποτυχημένα / όλα τα αιτήματα | διαθεσιμότητα |
| `replica_minutes` | το ολοκλήρωμα των pods στον χρόνο | κόστος |
| `correct_prov_pct` | % του χρόνου με **ακριβώς** όσα pods χρειάζεται το φορτίο, κατά τον πίνακα χωρητικότητας | ακρίβεια |
| `under_prov_s` / `over_prov_s` | χρόνος με λιγότερα / περισσότερα pods | πού χάνει ο καθένας |
| `recovery_s` | από το σφάλμα ως τη στιγμή που οι NFR ισχύουν για 60 s συνεχόμενα | MTTR |
| `k6_p95_s`, `k6_dropped` | από την πλευρά του χρήστη | επιβεβαίωση έξω από το cluster |

### 9.3 Στατιστική με μικρό n
Με 4 runs ανά μέθοδο δεν μπορείς να υποθέσεις κανονική κατανομή. Χρησιμοποιούμε **ακριβή τεστ**:
- **Fisher exact** (ανάκαμψη ναι / όχι): «αν οι δύο μέθοδοι ήταν εξίσου καλές, πόσο πιθανή είναι τόσο άνιση κατανομή
  επιτυχιών;».
  - v10: stuck 4/4 έναντι 0/4 → p = 0.014· cpuhog 4/4 έναντι 0/4 → p = 0.014·
  - όλα τα σφάλματα μαζί, 8/8 έναντι 0/8 → p = 0.00008 (v9: 7/8, p = 0.0007).
- **Permutation** (κόστος, παραβίαση): ανακατεύεις τις ετικέτες των runs με όλους τους δυνατούς τρόπους (70 για 4 + 4) και
  μετράς πόσο συχνά βγαίνει τόσο μεγάλη διαφορά.
  - **Το μικρότερο δυνατό p είναι 1/70 = 0.014.** Το κόστος το έπιασε και στις δύο καμπάνιες: κάθε run του agent ήταν
    φθηνότερο από κάθε run του HPA.
  - Η παραβίαση NFR του v10 έναντι του HPA: p = 0.071 (ένα run του agent είχε 0 s), άρα όχι σημαντική διαφορά. Στο v9 ήταν
    0.014.

### 9.4 Το πρωτόκολλο της καμπάνιας (`full_campaign.sh`)
- 4 runs ανά σενάριο ανά μέθοδο (24 συνολικά), με agent και HPA εναλλάξ.
- Η μνήμη αδειάζει στην αρχή. Είναι ανοιχτή στο κανονικό φορτίο, κλειστή στα σφάλματα.
- Κάθε run περιμένει ρεύμα. Ο agent ξεκινά μόνο αν το κύριο μοντέλο απαντήσει 3/3.
- Τα sha256 του κώδικα, του μοντέλου και των σεναρίων ελέγχονται από την αρχή ως το τέλος.
- Άκυρα runs (π.χ. μπαταρία) παίρνουν την ετικέτα `*-INVALID` και επαναλαμβάνονται. Αποτυχίες λόγω LLM **δεν**
  αντικαθίστανται.
  - Στην καμπάνια του v10 ο φορτιστής αποσυνδέθηκε για 26 s και 43 s: 2 runs άκυρα, επαναλήφθηκαν στο τέλος, αν και το
    αποτέλεσμά τους δεν θα άλλαζε.

## 12. Γλωσσάρι
- **NFR** (non-functional requirement): απαίτηση για το *πώς* λειτουργεί η υπηρεσία (latency, διαθεσιμότητα, κόστος).
- **SLO** (Service Level Objective): μετρήσιμος στόχος για μια NFR, εδώ p95 < 0.35 s και σφάλματα < 1%.
- **p95:** ο χρόνος κάτω από τον οποίο τελειώνει το 95% των αιτημάτων.
- **RED:** Rate, Errors, Duration· οι μετρικές συμπτωμάτων μιας υπηρεσίας.
- **MTTR:** μέσος χρόνος ανάκαμψης μετά από σφάλμα.
- **RAG:** ανάκτηση σχετικής πληροφορίας και ένθεσή της στο prompt.
- **ReAct:** ο βρόχος σκέψης, ενέργειας και παρατήρησης ενός agent.
- **Novelty detection:** εκπαίδευση μόνο στο φυσιολογικό, και επισήμανση κάθε απόκλισης.
- **Probe (readiness / liveness):** ερώτηση του Kubernetes προς το pod: «είσαι έτοιμο;» (βγάζει από την κυκλοφορία) /
  «ζεις;» (κάνει restart).
- **Rolling restart:** αντικατάσταση όλων των pods ένα-ένα, χωρίς διακοπή της υπηρεσίας.
- **Flapping:** εναλλαγή πάνω-κάτω χωρίς λόγο. Το αποφεύγουμε με νεκρές ζώνες και cooldowns.
- **Ανοιχτό / κλειστό μοντέλο φορτίου:** ρυθμός αφίξεων ανεξάρτητος από την απόκριση / χρήστες που περιμένουν την απάντηση.
- **Coordinated omission:** στο κλειστό μοντέλο, οι αργές απαντήσεις μειώνουν το φορτίο και κρύβουν το πρόβλημα.
- **Replica-minutes:** pods × λεπτά· το κόστος.
- **Intention to treat:** κάθε run που ξεκίνησε μετράει, και οι αποτυχίες δεν αντικαθίστανται.
