### 08:11 First stuck-fault run with the LLM agent: the agent diagnosed it correctly
Fault injected 08:11:15. Detector woke the agent within seconds (CPU 0.24, p95 rising).
- Memory offered two misleading "scale 1->2" hints (old entries have no p95, so latency was ignored).
- The agent **ignored them, called `get_kubernetes_logs()`, saw the DB-pool errors and restarted**,
  although the prompt's restart rule literally requires "CPU **and throughput** near 0" (throughput was ~4 rps).
  Root cause it wrote: *"DB connection pool exhaustion leading to high request latency and queueing.
  Action: Triggered a rolling restart."* Logins were back to 0.07 s right after.
- **But verification said UNSTABLE**: at +45 s the 1-minute windows still held the 3-s requests from before the
  restart (p95 3.8 s) and the new pod's startup burst (throttling 8%). So the fix was not saved to memory.

Fixes (apply to all later runs, "agent v3.1"):
- Verification now uses **40 s windows after a 50 s settle** (window = ~10–50 s after the action): measures only
  the post-action state. 30 s was tried first, but cAdvisor sometimes has < 2 samples in 30 s (empty result).
- Signature now includes p95 (`| P95:3.4s`), stored incidents keep p95; an incident with unknown p95 can no longer
  look "similar" to a state that breaks the latency SLO (+3 distance). Stuck state vs old overload memories: 0.x → 9.9.
